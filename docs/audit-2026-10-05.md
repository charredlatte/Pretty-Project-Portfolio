# Gateway and MCP audit, 5 October 2026

What was found by running the gateway and the Python MCP server under hostile and concurrent input, what is already
fixed, and what is not. Written for Charlotte, by ohwellwhy10-jpg, who runs a fork of this repository.

## How it was checked

- The gateway under `wrangler dev`, on a fresh state and on an upgraded one (the code at `0fefc36` writing the state, the
  fixed code reading it back): sign-ins, keys, OAuth grants, a held runner wait, routines.
- The Python MCP server over stdio and `--serve`, with 24 malformed messages and four processes writing at once.
- Sixty to a hundred seconds of mixed concurrent load: twenty agents, the runner's waits and says, routine writes,
  sign-in bursts from many addresses, WebSockets, MCP batches.
- Every in-repo caller of the changed tools, compared with what it really sends.
- Each finding below was reproduced a second time by someone who set out to refute it. Findings that did not reproduce,
  or that were behaviour by design, are left out. The fixes were then reviewed the same way: three reviewers, each
  finding reproduced and refuted by separate checks.

## Fixed in the fork

The fixes are `00d855f` and `9c29bb4`, merged there as PR 1 (https://github.com/ohwellwhy10-jpg/Pretty-Project-Portfolio/pull/1,
merge commit `a6f5bde`). Gateway tests: `harness/gateway/test/adversarial.test.mjs` (new, runs with `npm test`). Python
tests: `harness/test/test_mcp.py`.

| What | Why it matters | The fix |
|---|---|---|
| `CATIO_QUEEN` set to the same value as another key's secret (for example `CATIO_TOKEN`) | Every request returns 500, the café page included: the same hash is inserted twice and the unique-key error is rethrown at start | The duplicate is ignored with a warning, so a shared value can't also be the queen's key |
| An agents' key could call `inbox {agent: "queen", mark: true}` | It marks Charlotte's messages to the queen as handed over, so her runner never receives them | `inbox` for the queen is refused to agents' keys |
| An agents' key could call `report_status {agent: "queen"}` | It overwrites her presence record | Refused to agents' keys |
| Five wrong passwords locked a handle for fifteen minutes, from anywhere | Anyone who knows the handle can lock its owner out of sign-in, again and again | The lock counts by address: five at one handle from one address, twenty at any handles from one address, and a hundred at one handle from anywhere as a backstop |
| A non-form body to `/login` or `/authorize`; `answer` on a document that isn't a quiz | 500 instead of a refusal | 400 or a refusal |
| No way to end a browser's session | A cookie lasts a month | `POST /logout` (nothing in the page calls it yet) |
| The Python server stopped on malformed input (13 of 24 cases), lost writes between processes (92 of 160 kept), and `comments` limits of 0 or less misbehaved | One bad call ended a client's server | Arguments are checked against each tool's schema, a cross-process lock on `state.json`, limits clamped to 1 to 500 |

The backstop in the lock is a trade-off: a hundred wrong guesses at one handle from many addresses still lock sign-in
for everyone for fifteen minutes. A password of sixteen characters or more is what protects the account, and the lock
only limits the cost of guessing.

## Fixed in a second fork PR

https://github.com/ohwellwhy10-jpg/Pretty-Project-Portfolio/pull/5 (open when this was written; two commits on top of
`a6f5bde`). Each item has a test that fails without its fix.

1. **A message to the queen could be lost when the runner's connection drops mid-wait.** `queenReady()` marked notes
   handed over inside the wait, so a note given to a connection that had already gone was never offered again. The
   wait now carries `ack` (the newest note the runner was given) and a note is offered until then; a runner that sends
   no `ack` is handed each note once, as before.
2. **A password field of 32 MiB or more made `/login` and `/authorize` return 500** (the Durable Object RPC limit,
   reached before the handle check). The form is read with a 16 KiB cap and never held whole.
3. **An object such as `{"toString": 1}` as a field returned 500 in any tool call**, and in a document, a runner say, a
   stored routine, the MCP envelope and the owner's JSON routes. `src/plain.js` drops `toString` and `valueOf` keys
   at those doors.
4. **`decide` with a decider that answers `answers: null` returned 500** when `kind` was set; it is a refusal now.
5. **`queen.py` exited for good on a 503** and its wait thread died silently on a reply cut off half way. Both are
   waited out like any other error; only a refused key (401) stops it.
6. **Two regressions in the first fixes.** A routine whose turn ran longer than ten minutes was handed out twice (a
   streaming turn now renews its lease), and `catio_mcp.py` could fail to start in the seconds after a crash left a
   `state.lock` behind (it now waits long enough to take it over).
7. **The page's localhost check GETs `api/list_agents`**, which the Python server has answered with 404 since GET to
   `/api/*` was closed, so the page never connected to the local agents' server. It POSTs now.

## Still open

- **An agent's own `comment` marks the owner's earlier notes as read**, so a note sent a moment before an unprompted
  comment is never handed in. This is intended (`test_a_whole_visit`: "an answer means everything she said before it
  was read"), so it is a trade-off, not a bug, and was left as it is.
- **The runner acknowledges a note when it receives it**, not when its turn ends: a runner that crashes between the
  two still loses that note. Two runners on one key (unsupported) are each handed the same note until one
  acknowledges it.
- **If the queen calls the `inbox` tool on her own cat** between a wait's answer and her next wait, she is handed
  that note a second time. Her instructions don't mention `inbox`.
- **`StateLock` takeover in `catio_mcp.py`**: with several waiters on one stale lock at the same instant, more than
  one can proceed. Unchanged by the fixes; it needs a crash and a collision.
- **The single Registry object hashes every sign-in's password**, so a flood of guesses from many addresses slows
  every sign-in and key lookup behind it (already noted in `harness/gateway/README.md`).
